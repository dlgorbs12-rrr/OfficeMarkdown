# 대형 문서 변환 및 OCR 검증

2026-11-20, Windows 11 / Intel Core i7-12650H(10코어·16스레드) / 메모리 약 32GB에서 측정했다. 원본은 읽기 전용으로 사용했으며 사용자 문서, 변환본, 모델, 원본 경로와 실험 도구는 Git 제외 대상인 `local/`에 보관한다.

## 재현된 문제

기존 변환 함수를 사용한 순차 변환은 9분 0.7초에 메모리 보호 한도로 중단됐다. 직전 완료한 122개 Markdown은 기존 앱이 남긴 결과와 파일명·SHA-256이 모두 같았다. 다음 XLSX는 약 47MiB였으나, 한 시트의 XML은 약 452MiB였고 서식만 있는 셀이 약 1,888만 개였다. 이 파일을 읽는 8초 동안 Java 전용 메모리가 약 2.07GiB에서 6.17GiB로 증가했다. 해당 파일에는 삽입 그림이 없었다.

## XLSX 비교와 적용

새 Java 경로는 시트를 SAX로 한 번 읽고 표시할 셀만 임시 파일로 내보낸다. 빈 셀의 좌표는 기존 표 너비 계산에 반영하고, 공유 문자열도 디스크에서 조회한다. 전체 통합문서를 생성하지 않는다. 숫자·날짜·수식, 그림 위치, 실패 시 기존 Markdown 보존은 회귀 검증한다. 그림 XML과 공유 수식 정의까지 모두 디스크로 옮긴 구현은 아니다.

실제 문제 파일을 각 구현으로 3회 변환했다. Java는 JDK 21.0.4, 최대 힙 512MiB이며 Rust는 1.100.0 MSVC release와 calamine 0.38.0이다.

| 구현 | 변환 중앙값 | 최대 작업 집합 | 결과 |
| --- | ---: | ---: | --- |
| Java 스트리밍 | 7.05초 | 412.5MiB | 3회 완료·출력 해시 동일 |
| Rust 스트리밍 프로토타입 | 3.48초 | 약 4.81MiB | 3회 완료·출력 해시 동일, Java와 셀 내용 차이 |

두 구현의 시트 제목·표 헤더·셀 주소 4,457개는 같았지만, 셀 내용 471개가 달랐다. 작은 공통 파일에서도 Rust의 숫자·날짜·퍼센트 표시, 인라인 문자열 공백, 수식 캐시 기본값 차이가 확인됐다. 따라서 위 시간은 동일한 출력 품질의 가속 배수가 아니며, Rust 프로토타입은 제품에 넣지 않았다.

동일한 64MiB 힙에서 서식 셀 40만 개 합성 파일을 검사한 결과, 기존 Java DOM은 `OutOfMemoryError`로 종료됐고 새 경로는 약 0.81초에 완료했다. 공통 형식 파일과 서식 셀 2만 개 파일은 기존 변환 결과와 바이트 단위로 일치했다. 기존 실험은 JDK 22 기본 힙의 일괄 처리였으므로 그 메모리 값과 위 단일 파일 제한 힙 값을 완전히 동일한 조건으로 해석하지 않는다.

## OCR 엔진 비교

정답이 있는 합성 이미지 16장과 실제 PPTX에서 추출한 그림 16장을 고정했다. 모든 엔진에 같은 픽셀을 전달했다. 아래 문자 오류율(CER)은 합성 이미지에서 공백을 제외한 편집 거리이며 낮을수록 좋다. 표의 읽기 순서 차이도 오류에 포함한다. 실제 그림에는 정답을 붙이지 않았으므로 실제 문서의 인식 정확도 수치로 일반화하지 않는다.

Windows와 Tesseract는 3회, CPU 가속이 활성화된 PaddleOCR은 1회를 측정했다. Paddle은 CPU 4스레드 및 oneDNN을 사용했다. 비가속 Paddle의 미완료 실행은 결과에서 제외했다. 처리 시간은 초기 모델 로드를 제외한 실제 그림의 warm 요청 기준이다.

| 엔진 | 합성 CER | 숫자 토큰 일치율 | 실제 그림 중앙값 / p95 | 관측 프로세스 최대 작업 집합 |
| --- | ---: | ---: | ---: | ---: |
| Windows OCR, 한국어 | 38.91% | 58.7% | 161 / 557ms | 약 134MiB |
| Tesseract 5.5.4, best kor+eng | 23.98% | 71.7% | 645 / 3,316ms | 약 103MiB |
| PaddleOCR, 한국어 mobile | 1.81% | 100% | 2,287 / 5,846ms | 약 950MiB |

Paddle은 작은 글자 그룹에서도 높은 정확도를 보였으나 첫 시작 약 5.5초, 첫 요청 약 0.5초가 추가됐다. Windows를 기본 빠른 모드로 유지하고 Paddle을 한글 정밀 모드로 추가했다. Tesseract는 이 표본에서 속도·정확도 어느 쪽도 최선이 아니어서 제품 모드를 추가하지 않았다.

정밀 모드의 검증 버전은 PaddleOCR 3.3.2 / PaddlePaddle 3.2.2 / PaddleX 3.3.13, `PP-OCRv5_mobile_det` 및 `korean_PP-OCRv5_mobile_rec`이다. 추론에 쓰는 모델 파일을 미리 설치하고 네트워크 다운로드를 비활성화한다. Java와 Python은 한 작업에서 OCR 프로세스·모델을 재사용한다.

## 이미지 전달

PNG 대신 무손실 BMP를 쓰는 96쌍 비교에서 RGB와 인식 결과는 같았지만, 배치 전체 시간은 약 3.6% 늘었다. 실제 그림의 파일 쓰기 양도 약 63.6배가 되어 BMP를 기본 전송 형식으로 채택하지 않았다. 해상도를 낮춰 인식 내용을 잃는 방식도 적용하지 않았다.

PNG 압축을 낮춘 별도 96쌍 비교도 픽셀·인식 결과가 같았다. 실제 그림 처리 합계는 약 0.8% 줄었지만 전체 배치는 약 0.27% 늘고 실제 그림의 쓰기 양은 약 43.1% 증가했다. 일관된 속도 개선을 확인하지 못해 기존 PNG 압축을 유지했다.

## 통합 설치본 검증

그림 검색 변경과 통합한 최종 설치본의 JAR을 JDK 21 기본 힙으로 실행했다. 문제 XLSX는 10.75초에 완료됐고 최대 작업 집합 407.6MiB, 전용 메모리 676.9MiB를 기록했다. 원본 해시와 파일 속성이 일치했다. 이 변환본을 설치된 OfficeSearch에서 검색했고, 설치본 Paddle 워커로 한글과 숫자 인식 및 반복 요청을 확인했다.

- 기존 변환을 마쳤던 실제 XLSX 63개를 Windows OCR로 다시 처리했다. 49.43초, 경고 0건이었다. 시트 제목과 Markdown 표 행 기준으로 62개는 완전히 일치했다. 1개에서 수식의 쉼표 뒤 공백이 87곳 추가됐으며 그 밖의 표 내용 차이는 없었다. 그림 검색에서 추가한 메타데이터와 그림 자산은 이 대조 범위에서 제외했다.

## 재현 자료

### 대규모 시작 및 병렬 변환

격리된 폴더에 작은 합성 Markdown 파일 70,000개와 일치하는 제목 색인 70,000건을 준비했다. JDK 21, 최대 힙 256MiB에서 캐시 첫 500건 조회는 0.27초, Swing 화면이 500건을 표시하고 검색·파일 추가가 가능한 시점까지는 시험 코드 시작 후 1.05초였다. 변경 없는 파일 7만 개의 별도 백그라운드 확인은 1.48초였다. 이 시험은 이미 제목 색인이 있는 경우이며, 실제 고객 문서의 최초 본문·그림 색인 시간은 측정하지 않았다.

한글 그림 56장을 포함한 합성 XLSX 8개를 Windows OCR로 변환해 색인했다. 최대 힙 2GiB에서 파일 1개씩 처리했을 때 15.81초, 2개씩 처리했을 때 6.82초였다. Java와 자식 프로세스들의 작업 집합 합계 최대값은 각각 583MiB와 779MiB였다. 생성 식별자를 제외한 Markdown과 OCR 텍스트, 저장한 그림 및 미리보기는 일치했다. 각 설정을 한 번씩 순서대로 측정했으므로 캐시와 PC의 다른 작업도 시간에 영향을 줄 수 있다.

- 원래 장시간 실행: `local/real-probe/run-20261120-112247/`
- 자동 모드 추가 시험: 같은 8개 파일에서 힙 2GiB일 때 허용 한도 1→2→3→4, 7.50초, 최대 작업 집합 합계 914MiB. 힙 256MiB에서는 1개 유지, 12.83초. 두 실행의 변환 및 색인 건수와 OCR 출력이 일치했다. 세부 측정값은 `local/batch-parallel-check/`에 있다. 최종 설치본 JAR로도 7만 건 첫 목록과 검색·추가 활성화를 1.31초에 확인했다.
- Java 및 제한 힙·공통 형식 비교: `local/java-stream-bench/`
- Rust 구현·고정 Cargo 의존성·실측: `local/rust-stream-bench/`
- OCR 입력 정의·고정 버전·결과: `local/ocr-compare/`

프로젝트 개발 테스트는 `mvn test`, 로컬 앱 생성은 `build-local.ps1`을 사용한다. 원본이 필요한 성능 스크립트는 로컬 자료를 참조하므로 소스 배포에 포함하지 않는다.
